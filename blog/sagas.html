Sagas: where the work is kept.

A list per project of goals, tasks and subtasks, with who did each step, which model it ran on, and what it cost.

Written 2026-10-11 Cowork · X-ray · Sagas ← antiloki
in one paragraph

A saga is a goal and the tasks that get it done. You write one, or an agent’s plan becomes one by itself. Each task has an assignee, a status you can move on, and an activity trail that names who did each step. The time, cost and tokens on a task are the ones the run recorded, and a finished saga stays as part of the record. It lives in a file inside your project, and the agents can read it before they start.

1The problem: a to-do list inside one chat

Coding tools keep a plan, but the plan lives in the session that wrote it. Close the chat and the list goes with it. Run the same goal on another tool and you start again. Nothing says which model did which step, or what that step cost. With one agent that is a minor annoyance. With several agents on several subscriptions it is the thing you actually need to see.

2What a saga is

A saga is a titled goal. It holds tasks, and a task can hold subtasks (one level deep, so the list stays readable). A task is assigned to you, to Heimdall, or to an agent, and moves through todo, in progress and done. A saga’s own status is not typed in: it follows its tasks, and a failed run makes it failed.

The plan an agent writes for an ask becomes a saga on its own, with its steps as tasks, and they move as the run does. Anything you add by hand to such a saga is left alone. The screen follows the layout of an issues page: the list, a saga with its tasks, a task with its subtasks and a side panel of properties, with “New saga” and “New task”.

3Who did what, and with which model

Every line of the activity trail names its actor: you, Heimdall, or an agent. A task shows the agent’s face and the icon of the exact model that did it; one that failed carries a small red mark. On the list, each saga shows the faces of the agents behind it and the models they ran on, so a glance tells you whether this goal was done by Cursor’s Composer, by Gemini, or by both.

4The numbers come from the run

Time, cost and tokens on a task are what the run recorded for it; a saga adds up its tasks. We pointed it at the history of our own benchmark project: its 100 runs appeared as 100 sagas with 252 tasks (213 of them done) and about $4.20 of recorded cost, 67 sagas done, 19 failed and 14 canceled — each saga’s status being its run’s verdict, so a run that failed its QA reads as failed even when every task in it finished. Nothing was typed in.

5The agents read it too

antiloki gives its agents four tools for the list: read it, start a saga, add a task, update a task. An agent that reads it before it starts does not redo a task already marked done, and what it adds is attributed to it in the trail. Sub-agents, the workers inside a delegated run, can read the list but never write to it; the agent that delegated to them records what they found. That is the same rule that stops sub-agents from delegating further.

6A record, not a scratchpad

A finished saga cannot be canceled or deleted. The buttons are not there and the server refuses the request, so the history is the history. A canceled saga can be reopened, and adding a task to a finished one reopens it. Only a saga that is still open can be canceled or deleted.

7What it is not

It is not for a team of people: there are no mentions, notifications or permissions, because the team is you and your agents. It is not a board. It is one file per project (.antiloki/work.sqlite inside the project, on your machine), so each project has its own list. Importing issues from other trackers is not built.
